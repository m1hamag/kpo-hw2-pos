# ПОС. Преподавательская оценка студентов

ДЗ №2 по КПО. DDD, архитектура Ports and Adapters и паттерны GoF. Язык Go.

Консольный модуль, в котором преподаватель заводит студентов и рубрикатор,
выставляет, исправляет и отменяет оценки, смотрит итог и выгружает его в CSV.
Итог нигде не хранится, он всегда считается из текущих оценок и рубрикатора.

## Запуск

Нужен Go 1.22 или новее. Единственная внешняя зависимость это DI-контейнер
[`go.uber.org/dig`](https://github.com/uber-go/dig).

```bash
go run ./cmd/pos
```

```bash
go run ./cmd/pos -demo
```

```bash
go test ./...
```

```bash
go test ./... -coverpkg=./... -coverprofile=coverage.out && go tool cover -func=coverage.out | tail -1
```

- без флагов открывается меню, данные сохраняются в `pos.json` и подхватываются при следующем запуске;
- `-data файл.json` берёт другой файл, а `-data ""` работает без сохранения;
- `-demo` прогоняет сквозной сценарий из задания на заготовленном вводе и ничего не сохраняет. Ответы печатаются так, будто их ввёл пользователь, сам сценарий лежит в [`demo.go`](internal/adapters/primary/console/demo.go);
- дробные числа можно вводить через точку или запятую, на неверный ввод программа объясняет ошибку и спрашивает ещё раз;
- Enter вместо пункта меню показывает меню целиком, Ctrl+D нормально завершает работу.

## Функциональные требования

| Требование | Пункты меню | Где в коде |
|---|---|---|
| 1. Студенты и рубрикатор, добавить и посмотреть, удалить при необходимости | 1-6 | `app.Gradebook.AddStudent`, `RemoveStudent`, `AddCriterion`, `RemoveCriterion` |
| 2. Выставить оценку, посмотреть, исправить, отменить | 7-10 | `app.Gradebook.Grade`, `Correct`, `Cancel`, `Final` |
| 3. Балл в пределах критерия, оценка только по критерию из рубрикатора | везде | `domain.EvaluationFactory`, `domain.NewScore` |
| 4. Сквозной сценарий от студентов и критериев до экспорта итога | `-demo` | `console.DemoInput` |
| Итог по студенту и по всем, смена правила, выгрузка в CSV | 10-13 | `domain.FinalGradeService`, `app.Gradebook.ExportFinals`, `csvexport` |

## Архитектура

Выбрана **Ports and Adapters (Hexagonal)**. В центре домен, вокруг него
сценарии приложения, снаружи адаптеры. Primary-адаптер (консоль) вызывает
приложение, secondary-адаптеры (JSON-хранилище и CSV-выгрузка) реализуют
порты, которые объявлены внутри.

```text
cmd/pos/                          точка входа, флаги -data и -demo
internal/
  domain/                         ядро с сущностями, VO, инвариантами, фабрикой оценок,
                                  доменным сервисом итога и портами репозиториев
  app/                            сценарии (фасад Gradebook) и порт выгрузки FinalsExporter
  adapters/
    primary/console/              консольное меню, вызывает только app.Gradebook
    secondary/jsonstore/          репозитории домена поверх JSON-файла, DTO и маппинг
    secondary/csvexport/          выгрузка итогов в CSV, реализует app.FinalsExporter
  di/                             composition root, сборка графа в dig
```

Зависимости направлены внутрь, это видно по импортам пакетов.

```text
cmd/pos ──> di ──> console, jsonstore, csvexport, app, domain

console ──────> app ──> domain
csvexport ────> app
jsonstore ────────────> domain
domain  ──> только стандартная библиотека
```

- `domain` не знает ни про консоль, ни про JSON, ни про CSV. Теги `json:"..."` и DTO живут в `jsonstore`.
- Порты репозиториев (`StudentRepository`, `RubricRepository`, `EvaluationRepository`) объявлены в [`domain/repository.go`](internal/domain/repository.go), порт выгрузки `FinalsExporter` объявлен в [`app/ports.go`](internal/app/ports.go). Реализации лежат в адаптерах и про них знает только `di`.
- Пакет `dig` импортируют только `di` и `main`. Остальные получают зависимости через параметры конструкторов, контейнер никуда не передаётся, так что это не Service Locator.
- Папок "на вырост" нет, каждая папка содержит работающий код и тесты.

## Карта DDD

### Единый язык

| Слово из предметной области | В коде | Что это |
|---|---|---|
| студент | `domain.Student` | кого оценивают |
| критерий | `domain.Criterion` | за что ставят балл, у него есть максимум и вес |
| рубрикатор | `domain.Rubric` | набор критериев курса |
| оценка | `domain.Evaluation` | этому студенту по этому критерию поставили такой балл, с датой и комментарием |
| балл | `domain.Score` | сколько набрано из скольких возможных |
| итог | `domain.FinalGrade` | результат студента, посчитанный из его оценок и рубрикатора |
| правило подсчёта итога | `domain.FinalPolicy` | как именно из оценок получается итог |

Те же слова используются в меню, сообщениях об ошибках и в коде.

### Entity и Value Object

| Тип | Что это | Почему так |
|---|---|---|
| `Student` | Entity | различается по `StudentID`. Два студента "Иван Петров" с номерами 1 и 2 это разные люди |
| `Criterion` | Entity внутри агрегата `Rubric` | оценки ссылаются на критерий по `CriterionID`, а не по названию |
| `Evaluation` | Entity | её идентичность это пара (студент, критерий), `EvaluationKey`. Исправленная оценка остаётся той же оценкой с новым баллом |
| `Score` | Value Object | неизменяем, сравнивается по значению. Любые "8 из 10" равны между собой |
| `FinalGrade` | Value Object | неизменяемый результат подсчёта, нигде не хранится |
| `StudentID`, `CriterionID`, `EvaluationKey` | Value Object | идентификаторы |

Пример из тестов в [`model_test.go`](internal/domain/model_test.go).

```go
a, _ := domain.NewStudent(1, "Иванов Иван")
b, _ := domain.NewStudent(2, "Иванов Иван")
// a != b, это разные студенты с одинаковым ФИО

x, _ := domain.NewScore(8, 10)
y, _ := domain.NewScore(8, 10)
// x == y, балл определяется только своим значением
```

У всех доменных типов поля закрыты, создать их можно только через
конструкторы, которые проверяют данные. Оценку можно получить только из
`EvaluationFactory`.

### Агрегаты

- **`Student`**, отдельный агрегат из одной сущности.
- **`Rubric`**, корень агрегата с критериями внутри. Критерии добавляются и удаляются только через рубрикатор, поэтому номера уникальны, а названия не повторяются без учёта регистра.
- **`Evaluation`**, отдельный агрегат. На студента и критерий ссылается только по номерам. Оценок много, и они меняются независимо друг от друга, поэтому держать их внутри рубрикатора или студента было бы неудобно.

### Инварианты и где они охраняются

| Правило | Где проверяется |
|---|---|
| балл не выходит за пределы критерия | `domain.NewScore` и `Criterion.Score`. Других способов получить `Score` нет |
| оценку можно выставить только по критерию из рубрикатора | `EvaluationFactory.Create` ищет критерий в рубрикаторе |
| у студента по критерию не больше одной оценки | ключ оценки `EvaluationKey`. Повторно выставить нельзя (`ErrAlreadyEvaluated`), можно только исправить |
| итог согласован с текущим набором оценок | итог не хранится, `FinalGradeService` считает его каждый раз и проверяет, что оценки этого студента, по критериям из рубрикатора и без повторов |
| итог в пределах от 0 до 10 при любом правиле | `FinalGradeService` отклоняет результат стратегии вне шкалы |
| нельзя удалить критерий, по которому стоят оценки | `app.Gradebook.RemoveCriterion` (`ErrCriterionInUse`) |
| максимум и вес критерия больше 0, названия не пустые | конструкторы `NewCriterion`, `NewStudent` |

Через фабрику проходят и оценки, прочитанные из файла, а хранилище перед
каждой записью проверяет, что новое состояние потом загрузится. Поэтому
12 из 10 не появится даже из испорченного `pos.json`, программа просто не
запустится и скажет, что не так.

### Repository

Порты объявлены в домене, реализация одна, `jsonstore`. Репозитории отдают и
принимают целые агрегаты. `Rubric().Load()` каждый раз собирает новый
рубрикатор, поэтому изменения попадают в хранилище только после `Save`.

### Domain Service и Application Service

- **`domain.FinalGradeService`** это доменный сервис. Правило подсчёта итога не принадлежит одной сущности, ему нужны сразу рубрикатор (веса и максимумы) и все оценки студента.
- **`app.Gradebook`** это сервис приложения. Он сам правил не содержит, а загружает агрегаты из репозиториев, проверяет, что студент существует, вызывает фабрику и доменный сервис и сохраняет результат.

## Паттерны GoF

| Группа | Паттерн | Где | Какую боль закрывает |
|---|---|---|---|
| Порождающие | Фабрика | [`domain.EvaluationFactory`](internal/domain/evaluation.go) | Оценка рождается в одном месте, где проверяется, что критерий есть в рубрикаторе и балл в его пределах. Через неё проходят новые, исправленные и загруженные из файла оценки. Без фабрики эти проверки пришлось бы повторять в консоли, в сценариях и в хранилище |
| Структурные | Фасад | [`app.Gradebook`](internal/app/gradebook.go) | Консоль вызывает только фасад и не видит репозитории, фабрику и доменный сервис. Сценарии не размазаны по UI, а второй интерфейс, например HTTP, смог бы использовать тот же фасад без изменений |
| Поведенческие | Стратегия | [`domain.FinalPolicy`](internal/domain/policy.go) | Правило итога меняется. `WeightedPolicy` считает по всем критериям, нет оценки значит 0 баллов. `GradedOnlyPolicy` считает только по выставленным оценкам и показывает текущую успеваемость. Правило переключается прямо в консоли (пункт 12), `FinalGradeService` при этом не меняется. Новое правило это новый тип и одна строка в `di.Policies` |

### Чего специально нет

- **Builder для рубрикатора.** Рубрикатор заполняется по одному критерию из консоли, и каждый шаг сразу проверяется в `Rubric.AddCriterion`. Строителю тут нечего собирать.
- **Decorator для округления.** Округление одно, по правилам ВШЭ (половина вверх), поэтому это просто метод `FinalGrade.Rounded`.
- **Template Method для импорта ведомостей.** Импорта нет в требованиях, а паттерн без сценария был бы для галочки.
- **Интерфейс для фасада и отдельные "input ports".** Primary-адаптер один, а подменять фасад в тестах не нужно, он тестируется на хранилище в памяти.
- **Микросервисы, ORM, база данных.** Задание просит облегчённую версию, а JSON-файла хватает для одного преподавателя.

## DI-контейнер

Вся сборка лежит в [`internal/di/container.go`](internal/di/container.go).
`jsonstore` регистрируется как три репозитория домена, `csvexport` связан с
портом `app.FinalsExporter` через `dig.As`, дальше идут список правил,
часы, фасад и консоль. Объекты создаются один раз, поэтому все получают
одно и то же хранилище. `dig` проверяет граф только при запуске, поэтому
сборку проверяют тесты `TestContainer_*`, в том числе подмену экспорта
заглушкой через `Decorate`.
